# Card Image Pipeline

How card images move from ingestion to delivery, what lives where, and — important — a
documented gap in that history that predates this pipeline and was never recorded anywhere.

## Where images live

Two storage systems are involved, with different roles:

- **Supabase Storage** (bucket `card-images`) — the original ingestion target. `scripts/import-images.mjs`
  uploads raw PNGs here, at `<season>/<file>.png`, and this is where a brand-new card image lands
  first, before anything else touches it.
- **Cloudflare R2** (bucket `elements-card-images`, public host
  `https://pub-67aab109454d41809ce03ab0c1c9567d.r2.dev`) — the actual delivery source for the live
  app. Every currently-published `card_images` row's `image_url`/`thumbnail_url` points here, not
  at Supabase Storage. R2 holds three objects per image:

  ```
  card-images/<season>/<file>.png          original, untouched pixels (mirrored from Supabase Storage)
  card-images/<season>/grid/<file>.webp     400w, quality 82 — Cards-page tile / grid contexts
  card-images/<season>/thumb/<file>.webp    100w, quality 82 — small roster/lineup thumbnails
  ```

  The Supabase Storage original is **never deleted** once mirrored — it's left in place
  intentionally as a rollback safety net, the same approach the original 2025 R2 migration used
  (see `CHANGELOG.md`, v1.3.0).

## How an image gets from one to the other today

Two scripts, chained:

1. **`scripts/import-images.mjs`** (`npm run import:images -- <season>`) — matches local image
   files (from `ELEMENTS_CARD_IMPORT_FOLDER`) to `cards` rows by filename/team/year, uploads each
   to Supabase Storage, and upserts a `card_images` row pointing at the Supabase Storage URL. This
   script has never written to R2 directly — it only knows about Supabase Storage.
2. **`scripts/sync-images-to-r2.mjs`** (`npm run sync:images-to-r2`, or run automatically as the
   second half of `npm run import:images -- <season>`) — finds every `card_images` row still
   pointing at Supabase Storage, mirrors the original into R2 unchanged, generates the `grid.webp`
   and `thumb.webp` variants via the shared module below, uploads all three, then repoints that
   row's `image_url`/`thumbnail_url` at the new R2 object. Idempotent and resumable: a row already
   on R2 is skipped, so it's always safe to re-run.

Resize settings and the R2 key convention live in exactly one place —
**`scripts/lib/imageVariants.mjs`** — imported by both `sync-images-to-r2.mjs` and
`scripts/generate-image-variants.mjs` (the one-time backfill script, below), so the two variant
files are never generated by two different code paths.

### The one-time backfill

Before `sync-images-to-r2.mjs` existed, the entire published catalog (13,449 rows, spanning every
season from 1871–2025) was already on R2 with no variants. `scripts/generate-image-variants.mjs`
(`npm run generate:image-variants`) backfilled `grid.webp`/`thumb.webp` for all of them in one
pass. Result: **13,444 of 13,449 succeeded.** The remaining 5 have no source image in R2 at all —
a pre-existing, unrelated gap, not something this pipeline can fix:

- Bill Nuttall 1925 TOT
- Evelio Hernandez 1956 WSH
- Drew Butera 2015 KCR
- Connor Overton 2021 TOT
- Grady Sizemore 2015 TOT

## What the variant files are for, and current app read status

`grid.webp` and `thumb.webp` exist in R2 for 13,444 rows today, but **the app does not read them
yet.** `card_images.image_url`/`thumbnail_url` still point at the full-size original PNG
everywhere — Cards-page tiles, roster thumbnails, and every other display context all download the
same ~800KB–1.2MB original regardless of how small it's actually rendered. Wiring the app to
select the right variant per display context is **Piece 3**, not yet started.

One related piece of dead code worth knowing about: `src/utils/cardHelpers.ts`'s
`normalizeImageUrl()` still contains a runtime rewrite for `.../storage/v1/object/public/card-images/2025/...`
URLs → R2. It was written for the original v1.3.0 2025-only migration, back when the DB was
expected to still hold Supabase Storage URLs for 2025. It currently matches **zero** rows (every
row's URL is already a direct R2 URL), so it's inert — left as-is, not touched by this pipeline
work, flagged here so a future cleanup pass knows why it's there and that it's safe to remove once
confirmed still unused.

## Known gap: the historical migration has no recorded process

This is the important part to not silently paper over. The 2025-season migration (2,310 objects,
Supabase Storage → R2) is documented in `CHANGELOG.md` under v1.3.0, including that it was done
with `rclone` and verified with `rclone check`. That's the *only* migration event with any record
at all.

But every other season — roughly **11,100 additional images**, 1871 through 2025 minus the 2,310
already covered — was **also** migrated to R2 at some point, with:

- No corresponding CHANGELOG entry.
- No script anywhere in this repo's git history (`import-images.mjs` has been byte-identical since
  the initial commit and has never written to R2; the only commit that touches R2 at all,
  `14d243d`, only added the now-dead `normalizeImageUrl()` rewrite — no migration script was ever
  committed alongside it).
- No trace of *how* the `card_images.image_url` column itself got rewritten from Supabase Storage
  URLs to direct R2 URLs for these rows, since the CHANGELOG's documented 2025 approach relied on a
  runtime rewrite, not a DB mutation — yet the DB rows for 2025 (and every other season) hold
  direct R2 URLs today regardless.
- An undocumented `r2_object_key` column on `card_images` that isn't written by any script in this
  repo, isn't referenced anywhere in `src/` or `scripts/`, and isn't defined in any tracked
  Supabase migration — it simply exists, populated, on every row, presumably by whatever process
  did this migration. (It turned out to be genuinely useful — it's what made a clean, precise
  recovery possible after an accidental live-import regressed 9 rows on 2026-08-24 — but its origin
  is exactly as undocumented as everything else here.)

If this ever needs to be redone, audited, or extended (e.g. a future storage-provider change),
there is no recorded procedure to follow — treat that as a known, flagged risk, not an assumption
that "someone probably has a script for it somewhere."

## Commands

```bash
npm run import:images -- <season>   # import + sync chained (see note below on running this)
npm run sync:images-to-r2           # sync step alone, for rows already imported to Supabase Storage
npm run generate:image-variants     # one-time backfill; supports --dry-run, --force, --limit=N, --only-season=YYYY
```

**All three write to production Supabase and/or R2.** Per the working-style rule in `CLAUDE.md`,
none of these should ever be run as a side effect of checking something else — running one of them
must be the explicit, singular, confirmed purpose of that command.

## 2026-08-26 — 5 rows recovered from the health-audit's "130 broken images" finding

5 published cards had `card_images` rows with correctly-shaped `image_url`/`r2_object_key` values
that pointed at nothing — no object at that key in R2 at all (found and reconciled during the
2026-08-25 health audit; see that report's Category 6). All 5 turned out to have a real source PNG
in the raw per-manager Drive folder (`.../Elements Baseball League/<Manager>/<Year>/`), once Google
Drive for Desktop gave real local filesystem access to it — including Grady Sizemore 2015 TOT,
which an earlier (undocumented, ChatGPT-assisted) search had concluded didn't exist anywhere; it
was in `Will/2015/TBR Grady Sizemore.png`, exactly where the row's own `drive_folder_name` metadata
already said it was.

Fixed with a narrow, single-purpose script (not committed — one-off, hardcoded to these 5
`card_key`s, not reusable tooling) that uploaded each original PNG to R2 at the row's own
already-correct `r2_object_key`, generated the same grid/thumb WebP variants via
`scripts/lib/imageVariants.mjs` (the same shared module `sync-images-to-r2.mjs` and
`generate-image-variants.mjs` use, not reimplemented), and updated `image_url`/`thumbnail_url`/
`last_synced_at`. Deliberately did not touch `import-images.mjs`'s season-wide batch path, since
the 5 rows span 4 different seasons and a full-season reimport would have been a disproportionate
blast radius for 5 rows.

Rows fixed: `Bill Nuttall 1925 TOT`, `Evelio Hernandez 1956 WSH`, `Drew Butera 2015 KCR`,
`Connor Overton 2021 TOT`, `Grady Sizemore 2015 TOT`. Verified with real `HeadObjectCommand` checks
against R2 (independent of the fix script's own reported success) for all 15 objects (5 originals +
5 grid + 5 thumb), plus live rendering confirmed in the app for two of the five.
